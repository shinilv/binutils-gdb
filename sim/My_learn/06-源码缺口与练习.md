# 06 源码缺口与练习

这个目录是教学示例，不应把它当作已覆盖所有边界条件的参考实现。以下结论来自对架构规范、实现和 testsuite 的交叉阅读。

## 1. 已发现的规范/实现缺口

### 1.1 空栈 POP/RET 没有检测

规范要求：

```text
POP 空栈 = error
RET 空栈 = halt
```

实现没有记录栈深度，只是直接修改 SP 后读取：

```text
初始 SP=0x80000
空栈 POP/RET -> SP=0x80002 -> 读取未使用位置
```

因此空栈 RET 可能读到 0 并跳到地址 0，而不是按规范停机。

合理修复方向：在 `example_sim_cpu` 中增加 `stack_depth`，PUSH/CALL 增加，POP/RET 先检查再减少。不能只用 `sp == 0x80000` 判断而忽略当前 push/pop 的先后约定。

### 1.2 MOD 没有处理除数为零

实现直接执行 C 表达式：

```c
result = num3 % num4;
```

当 `num4 == 0` 时是 C 未定义行为。架构规范没有明确规定结果，模拟器至少应该确定性地以某种错误停止，而不是让宿主进程发生不可预测行为。

### 1.3 opcode 被当作普通值解释

实现取到 opcode 后调用：

```c
num1 = interp_num(cpu, iw1);
```

若指令位置出现 `32768`，它会读取 R0 的值；假如 R0 为 19，就可能把这个 word 当成 OUT。规范只说明“operation argument”遇到寄存器编码时应解引用，opcode 本身通常应直接限制为 `0..21`。

更严格的实现应直接验证 `iw1 <= 21`，不通过 `interp_num` 解引用 opcode。

### 1.4 逻辑上的无界栈并不真的无界

实现把栈放在默认 16 MiB sim 内存中，从 `0x80000` 向下增长。它没有栈溢出或与其他映射区冲突检查。这是工程上的简化，而非规范中“unbounded stack”的严格实现。

### 1.5 IN 的字符符号扩展

输入缓冲变量是 `char c`。在 `char` 默认有符号的平台，输入 `0x80..0xff` 后赋给 `uint16_t` 可能产生 `0xff80..0xffff`，超出 15 位有效范围。Challenge 假设普通小写输入，所以原任务通常不受影响；更稳健的实现可使用 `unsigned char` 并决定如何验证范围。

### 1.6 重新创建 inferior 不等于完整复位

`initialize_cpu` 在 `sim_open` 时清零寄存器并初始化 SP；`sim_create_inferior` 只显式设置入口 PC。如果同一个 simulator 实例多次创建 inferior，需要检查期望是否是保留状态，还是应该显式执行架构复位。

## 3. 推荐练习顺序

### 练习 1：纸上执行

手工推演以下程序，分别记录每一步的 byte PC、R0、R1 和输出：

```text
1,32768,65,       # SET R0,65
19,32768,         # OUT R0
9,32769,32768,1,  # ADD R1,R0,1
19,32769,         # OUT R1
0                 # HALT
```

预期输出 `AB`。预期 PC 序列：`0 -> 6 -> 10 -> 18 -> 22`，随后在 byte 22 执行 HALT。

### 练习 2：增加 `jt.s`

在 testsuite 中覆盖两条路径：

```text
JT 0,target      不跳
JT 1,target      跳
JT r0,target     寄存器条件
```

先照 `jmp.s`、`gt.s` 的风格写，不要改 simulator。

### 练习 3：增加输入回显测试

写程序：

```text
IN R0
OUT R0
HALT
```

先调查 DejaGNU 的 `run_sim_test` 怎样提供 stdin。这个练习的重点是测试基础设施，不只是 opcode。

### 练习 4：复现空栈 RET 问题

写只有 `RET` 的程序，打开 instruction/register/memory trace，观察它是否跳回 0。先用测试证明行为，再考虑修改结构体和语义。

### 练习 5：补栈深度

建议步骤：

1. 在 `example_sim_cpu` 增加深度字段；
2. 在 `initialize_cpu` 清零；
3. PUSH/CALL 成功后增加；
4. POP 空栈时以错误停止；
5. RET 空栈时正常 HALT；
6. POP/RET 成功后减少；
7. 添加正常和空栈测试。

### 练习 6：让 opcode 验证更严格

先构造一个程序：第一 word 是 32768，并预先使 R0 等于某个 opcode。确认当前实现的行为，再修改为 opcode 必须是字面量 `0..21`，最后加入回归测试。

### 练习 7：把长 `if/else` 重构成表驱动译码

完成前面练习后再考虑。可以定义：

```c
struct opcode_desc {
  const char *name;
  unsigned operands;
  void (*execute)(...);
};
```

但不要为了“代码短”牺牲可读性。这个示例的长 `if/else` 很直白，适合初学者把每条语义与源码一一对应。重构的目标应是减少重复的取参/校验代码，并保持 trace 信息准确。

## 4. 移植一颗新 CPU 时可复用的清单

从这个例子推广到自己的架构时，至少回答：

```text
[ ] 架构私有 CPU 状态有哪些寄存器？
[ ] PC 的内部单位是 byte、halfword 还是 instruction index？
[ ] 目标端序和对齐规则是什么？
[ ] 程序由 BFD/ELF 如何加载？入口地址从哪里来？
[ ] 取指、读数据、写数据分别使用哪个 sim map？
[ ] opcode 与操作数如何验证？
[ ] 正常退出、非法指令、访存 fault 如何报告？
[ ] 单步执行后是否调用 event tick/process？
[ ] PC fetch/store 回调是否注册？
[ ] I/O 或系统调用是否通过 callback？
[ ] trace 能否分别看到取指、译码、寄存器、内存和分支？
[ ] testsuite 是否覆盖正常、边界和错误路径？
```
