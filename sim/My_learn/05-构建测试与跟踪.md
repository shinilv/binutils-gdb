# 05 构建、测试与跟踪

## 1. 环境建议

binutils-gdb 使用 Autoconf/Automake/Make 工作流。在 Windows 上，优先使用 WSL 或配置完整的 MSYS2/Cygwin 环境；以下命令按 POSIX shell 编写。

常见依赖包括：

```text
C 编译器、make、bash、bison、flex、texinfo
DejaGNU/runtest（运行 testsuite 时需要）
```

具体依赖随仓库版本和系统发行版而变化。先运行 `configure`，按它报告的缺失项补齐即可。

## 2. 使用独立构建目录

不要在源码目录里直接构建。假设当前目录是 `binutils-gdb` 的父目录：

```sh
mkdir -p build-synacor
cd build-synacor
../binutils-gdb/sim/configure --enable-example-sims
make -j"$(nproc)"
```

生成的独立运行器通常位于：

```text
build-synacor/example-synacor/run
```

`sim/configure.ac` 只有在显式指定 `--enable-example-sims` 时才调用 `SIM_BUILD_TARGET([example-synacor])`。

## 3. 运行 testsuite

在构建目录尝试：

```sh
make check RUNTESTFLAGS="example-synacor/allinsn.exp"
```

若需要查看详细日志，检查构建目录下 testsuite 产生的 `.log` 和 `.sum` 文件。没有安装 DejaGNU 时，构建系统通常会提示找不到 `runtest`。

## 4. testsuite 如何伪造汇编器支持

[`testsuite/example-synacor/isa.inc`](../testsuite/example-synacor/isa.inc) 定义：

```asm
.set r0, 32768
...
.macro ADD a:req, b:req, c:req
    _op 9, \a, \b, \c
.endm
```

底层 `_op` 宏把每个数拆为低字节、高字节：

```asm
.byte value & 0xff, (value >> 8) & 0xff
```

因此这里没有真正的 Synacor GAS 后端。主机 assembler 只是在 ELF 的 `.text` 中放置指定字节；模拟器加载 ELF 后把它们解释为 Synacor 指令。

`allinsn.exp` 将 linker 参数设为：

```text
-Ttext=0
```

确保 `.text` 从地址 0 开始，符合架构规范。

## 5. 测试的 pass/fail 约定

`testutils.inc` 的 `pass` 宏输出：

```text
pass\n
```

然后 HALT。许多测试开头是：

```asm
JMP 3
HALT
```

后续断言失败时执行 `JF ..., 2`，跳回 word 地址 2 的 HALT。这样失败路径不会输出期望的 `pass`，DejaGNU 就会判断失败。

## 6. 适合精读的三个测试

### `add.s`

验证：

- 立即数和寄存器源操作数；
- 目标寄存器写入；
- 模 32768 回绕。

其中 `0x7ffe` 可理解为模 32768 意义下的 `-2`：

```text
104 + 32766 mod 32768 = 102
```

### `call.s`

CALL 位于 word 0，长度为 2 words，因此返回地址应为 word 2。目标代码直接 POP 检查栈顶是否为 2，这个测试没有执行 RET，却精确验证了 CALL 保存的地址单位。

### `mem.s`

它先读取程序中的 JMP 参数，再用 WMEM 把参数从 14 改为 3，最后跳回 0。重新执行 JMP 时跳到 `pass`，验证了读写内存、word/byte 地址换算和自修改代码。

## 7. 运行时跟踪

构建包含相应 trace 支持后，可尝试：

```sh
./example-synacor/run --trace-insn program.elf
./example-synacor/run --trace-extract --trace-decode program.elf
./example-synacor/run --trace-register --trace-memory program.elf
./example-synacor/run --trace-branch program.elf
./example-synacor/run --trace program.elf
```

如果运行器提示某种 tracing “not compiled in”，说明当前构建配置没有启用该类别，并不表示指令实现出错。先用 `./example-synacor/run --help` 查看当前二进制实际支持的选项。

## 8. 裸 Synacor binary 与 ELF

`nrun.c` 会用 `bfd_openr` 并要求 `bfd_check_format(..., bfd_object)` 成功。因此不能假定原始 Challenge `.bin` 可直接运行。可选思路有：

1. 像 testsuite 一样把字节封装到 ELF `.text`；
2. 使用 `objcopy` 的 binary input target 转换并设置 section 地址/入口；
3. 写一个小转换工具产生包含 `.text` 和入口地址的 object；
4. 修改或另写前端，直接把裸文件加载到地址 0。

学习阶段优先复用 testsuite 的 `.s` 宏和 ELF 流程，因为它能同时练习 linker 地址、BFD loader 和 simulator。

## 9. 最小调试策略

遇到某条指令失败时按这个顺序检查：

```text
原始字节是否为小端
  -> ELF .text 的 VMA 是否为 0
  -> PC 当前使用 byte 还是 word 单位
  -> 目标操作数是否必须是寄存器
  -> 源寄存器是否已通过 interp_num 解引用
  -> 顺序 PC 增量是否等于指令 word 数 * 2
  -> sim_engine_halt 的 reason/status 是否正确
```

同时打开 `extract + decode + register + branch/memory` 跟踪，通常可以很快定位在哪一层出现偏差。
